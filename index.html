01 / Capabilities

Everything you need to
author a scene. Nothing you don't.

01

Timeline-authoring camera

Place keyframes along the scroll track and set the camera pose at each one. The runtime interpolates between them with per-segment easing, so the camera move is a design decision you actually make.

02

Two modes, no ambiguity

In Scene mode the gizmo edits the object's base transform. In Preview mode it edits the active keyframe's override. Sculpting a shape can never accidentally change your camera choreography.

03

Edits that survive dragging

Property panels refresh values in place rather than rebuilding the DOM, so a slider never disappears from under the pointer mid-drag. Keyframe markers behave the same way.

04

Export that is just files

A build produces a folder you can drop on any static host. No server component, no database, no vendor account between you and your own work.

02 / Workflow

Three steps, and the
third one is optional.

  1. Step one

    Build the scene

    Add primitives, set materials, place lights. Work in Scene mode where the camera is yours and every object sits at its resting transform.

  2. Step two

    Choreograph the scroll

    Switch to Preview, scrub the timeline, and capture poses into keyframes. Add looping spin and bobbing motion for anything that should move on its own.

  3. Step three

    Export, then keep editing

    Ship the bundle. The same scene file reopens in the editor for the next pass — there is no round-trip conversion to lose your work in.

03 / The format

A scene is a
readable file.

No proprietary binary, no locked project format. It is JSON you can diff, review, hand-edit, and generate. Each keyframe resolves into a complete pose per object: anything it mentions merges over the base transform, anything it does not mention keeps the base transform.

That rule is why adding an object never retroactively breaks the keyframes you already authored.

scenes/demo.json 
{
  "objects": [{
    "id": "obj_knot",
    "geometry": { "type": "torusKnot", "args": [1.05, 0.3, 220, 32] },
    "material": {
      "type": "physical",
      "color": "#b39dff",
      "metalness": 0.9,
      "roughness": 0.14
    },
    "spin": [0, 0.16, 0]
  }],

  "scroll": {
    "length": 420,
    "easing": "easeInOut",
    "keyframes": [{
      "at": 0,
      "label": "Establish",
      "camera": {
        "position": [0, 3.2, 13.5],
        "target": [0, 1.5, 0]
      },
      "objects": [{
        "id": "obj_knot",
        "transform": { "scale": [0.85, 0.85, 0.85] },
        "opacity": 0.9
      }]
    }]
  }
}

05 / Questions

Reasonable things to ask.

Do I need to know three.js?

Not to author a scene — the editor covers transforms, materials, lights, and camera keyframes. You will want it if you plan to extend the runtime with custom geometry or shaders, which is the intended way to go beyond primitives.

Can I load my own models?

Not yet. This ships with primitives only. A GLTF loader is the highest-value next addition and the scene format already has room for a model geometry type without breaking existing files.

What happens on low-end devices?

The renderer clamps device pixel ratio at 2 and shadow maps are a single directional light. It also honours prefers-reduced-motion, in which case the scroll panels drop into normal document flow and the 3D backdrop becomes a still.

Is the scene format versioned?

It carries a version field and scenes are validated on load — structural problems are reported rather than silently rendering wrong. A version is cheap to add now and expensive to add later.
